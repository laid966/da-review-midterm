SQL：从 schema 到外连接Introduction to SQL高频

覆盖 p5–p108（SQL Part I 基础查询 + Part II 集合运算/嵌套/聚合/NULL/外连接）。本讲是半期卷面分值最集中、最容易靠练习拿满的一讲：既有"写查询"也有"算行数/算聚合"的计算题。

🎯 本节考什么

  • 会算：给定小表，手算 join 的输出行数、GROUP BY + HAVING 的每组聚合值、三值逻辑下某元组是否被 WHERE 保留、multiset 运算后的重复次数。
  • 会背：join 的三步语义（笛卡尔积→过滤→投影）；GROUP BY 的语义四步；三值逻辑的 min/max/1−x；inner 与三类 outer join 的保留规则；key 与 foreign key 的定义。
  • 会区分：WHERE vs HAVING；UNION vs UNION ALL；INNER vs LEFT/RIGHT/FULL OUTER；IN vs EXISTS vs ANY/ALL；GROUP BY vs 嵌套查询（效率）；key vs foreign key。

核心概念 1：关系模型——表、schema、键与约束

SQL 既是 DDL（定义 schema，create/alter/delete 表与属性），也是 DML（插入/删除/修改元组，以及查询）。它是声明式的高级语言：你只写"要什么"，由优化器决定"怎么算"——课件甚至说它大概是"世界上最成功的并行编程语言"（parallel programming language，暗示多核时代的并行计算）。

表 = 元组的 MULTISET

课件定义：一个 relation（表）是 multiset of tuples，其属性由 schema 指定。四个词必须分清：attribute（列）是有原子类型的条目；tuple（行，也叫 record）是一条记录；cardinality 是元组个数；arity 是属性个数。multiset 是"允许重复的无序表"：列表 [1,1,2,3]、集合 {1,2,3}、multiset {1,1,2,3} 三者不同，并且 multiset 没有 next() 方法——行序本质无序，这也是 ORDER BY 存在的理由。

数据类型：字符 CHAR(20) / VARCHAR(50)；数字 INT / BIGINT / SMALLINT / FLOAT；其它 MONEY / DATETIME。每个属性必须是原子类型（不能是 list/set），所以关系表是"平的（flat）"。判断题"一张表的某列可以存数组"→ 标准 SQL 里错。

例：Product(PName, Price, Category, Manufacturer) 的 arity = 4；若表里 4 行，cardinality = 4；两行完全相同也合法（multiset）。

Key：最小唯一标识

定义要背原话：key 是属性的最小子集，能唯一标识关系中的元组；作为约束，它的含义是"若两个元组在 key 上取值相同，则它们必是同一个元组"。三个高频问答：① key 一定存在吗？不一定，必须在 CREATE TABLE 里显式声明，不声明就没有；② 一张表能有几个 key？primary key 只能一个，但 candidate key / unique 约束可以有多个（如 sid 与 email 都唯一时，选一个当 primary，另一个仍可作为 unique key）；③ 复合键：Enrolled(student_id, cid) 用两列一起当主键，单独任何一列都不唯一。

Foreign Key：跨表引用

课件场景：Enrolled(student_id, cid, grade) 里 student_id 单独不是 key（一个学生选多门课），但它必须指向 Students 里已存在的学生，否则违反"只有正式学生才能选课"。写法：

CREATE TABLE Enrolled(
  student_id CHAR(20),
  cid        CHAR(20),
  grade      CHAR(10),
  PRIMARY KEY (student_id, cid),
  FOREIGN KEY (student_id)
    REFERENCES Students(sid)
)

两个必考后果：插入不存在的 student_id → INSERT 被拒绝（foreign key 是约束，不是提示）；删除被引用的学生 → 由 DBA 选策略：① 禁止删除；② 级联删掉该生所有选课记录；③ 把引用置为 NULL（SQL 允许的第三种做法，要求该列可空）。

key vs foreign key（选择题最爱）
维度Key / Primary KeyForeign Key

能否重复不能（唯一）能（很多选课共享同一个 student_id）
能否为 NULL主键不能可以（若该列可空；NULL 表示未知/不适用）

schema 与约束不只管"正确性"，也是优化的依据（课件 p19）：知道 sid 唯一，优化器就能选更快的 join 计划；知道某列 NOT NULL，就能省掉一批 NULL 判定。所以"约束让插入变慢"与"约束让查询变快"是同一件事的两面，答题时两句都写才完整。

为什么一般情况下不写 general constraints（如"数据库课不能有 25 人"）：性能。课件原话——每当要做丑事（或避开便利），都是为了性能；约束越自由，每次插入的检查代价越高。

核心概念 2：单表查询——SFW 与六个细节

基本形式三行，课件叫它 SFW query：

SELECT <attributes>
FROM   <Table>
WHERE  <conditions>

两个操作名来自关系代数：Selection（选择）按条件筛元组（行），Projection（投影）输出属性子集（列）。注意投影不自动去重，重复行照留，除非写 DISTINCT。

六个一考就错的细节

  • 大小写：SQL 命令与表名/列名不敏感（SELECT = select，Product = product）；但字符串值敏感（'Seattle' ≠ 'seattle'）。
  • 引号：常量用单引号 'abc'；双引号 "abc" 在标准 SQL 里是标识符（列名），不是字符串。WHERE Category = "Gadgets" 在标准 SQL 里是错的。
  • LIKE：模式匹配，两个通配符 —— % 任意长度字符序列（含空串），_ 恰好一个字符。'%gizmo%' 匹配任何包含 gizmo 的串。
  • DISTINCT：作用于整个 SELECT 列表，不是某一列。SELECT Category 返回两个 Gadgets；SELECT DISTINCT Category 只剩三个值。
  • SELECT 列表可写表达式与别名：SELECT PName, Price*0.9 AS SalePrice；SELECT * 带出全部属性（问"输出 schema 有几个属性"时要数清）。
  • WHERE 先于 SELECT 生效：所以 WHERE 里既不能引用 SELECT 刚起的别名（WHERE SalePrice > 10 报错），也不能用聚合函数。

ORDER BY 与输出 schema

ORDER BY Price, PName：先按 Price 升序，Price 相同的用第二个属性破平；默认 ASC，降序写 DESC。课外补充：NULL 在排序中排最前还是最后由 DBMS 决定（SQL 标准未统一），题目没说明就不必纠结。

例：SELECT PName, Price FROM Product WHERE Category = 'Gadgets' ORDER BY Price DESC；输入 schema 是 Product(PName, Price, Category, Manufacturer)，输出 schema 只有 (PName, Price)——常问"输出几个属性"，看 SELECT 列表即可。

核心概念 3：多表查询——join 的三步语义

课件反复强调：join 的语义（semantics）是"先笛卡尔积 → 再按条件过滤 → 最后投影"。这不是 DBMS 的执行顺序（课件专门澄清：说的是 semantics，不是 execution order），但它决定查询"应该"返回什么，是所有反直觉题的推理工具。

  1. 笛卡尔积（cross product）：X = R × S，取所有元组组合，共 |R| × |S| 行。
  2. 选择/条件（selection）：Y = { x ∈ X | Conditions(x) }，连接条件与普通过滤条件一起作用。join = 笛卡尔积再过滤。
  3. 投影（projection）：只保留 SELECT 里点名的属性。
Answer = {}
for x1 in R1:
  for x2 in R2:
    if Conditions(x1, x2):
      Answer = Answer ∪ {(x1.a1, x2.a2)}
return Answer        # 注意：multiset 并，不去重

把 join 实现成嵌套循环就是上面的二重循环——所以漏写连接条件时结果会退化成一个巨大的笛卡尔积，这是"查询为什么返回 N×M 行"的第一诊断点。

会算：join 的中间结果有多少行

三步里每一步的行数都能算，这是"给两张小表问结果行数"的固定套路：① 笛卡尔积 = |R| × |S|；② 过滤后 = 满足连接条件与过滤条件的组合数（一个 R 元组匹配 k 个 S 元组就产生 k 行）；③ 投影不改变行数，除非 DISTINCT。所以结果行数 = 左表行数 × 平均匹配数。

例：R 有 3 行、S 有 4 行，条件 R.A = S.B，若 R 的每个值在 S.B 中平均出现 2 次，则结果 3 × 2 = 6 行；若连接列在 S 上是 key（唯一），结果最多 3 行。反过来，若结果恰好是 3 × 4 = 12 行，说明条件里很可能根本没有连接条件。

反直觉题：空表 + OR 条件

课件那道题：SELECT DISTINCT R.A FROM R, S, T WHERE R.A = S.A OR R.A = T.A，看起来像 R ∩ (S ∪ T)，但若 S 为空，结果也是空集——S 为空时 R × S × T 本身就是空，后面的 OR 根本无从作用。结论：永远用语义（笛卡尔积）验算，别凭"看起来像集合运算"下结论。

三种等价写法 + 元组变量歧义

找"日本制造、价格不超过 200 的产品名与价格"：

SELECT PName, Price
FROM   Product, Company
WHERE  Manufacturer = CName
  AND  Country = 'Japan'
  AND  Price <= 200

-- 等价写法（inner join）：
SELECT PName, Price
FROM   Product JOIN Company
       ON Manufacturer = CName
WHERE  Country = 'Japan'
  AND  Price <= 200

元组变量歧义：Person(name, address, worksfor) 与 Company(name, address) 同时在 FROM 里时，SELECT DISTINCT name, address FROM Person, Company WHERE worksfor = name 的 name/address 指哪张表？标准做法是表名限定或别名：SELECT DISTINCT Person.name, Person.address FROM Person, Company WHERE Person.worksfor = Company.name，或 FROM Person p, Company c WHERE p.worksfor = c.name。答题一律写限定名，既清楚又免除歧义。

核心概念 4：集合运算与 MULTISET 语义

三个显式运算符：INTERSECT（交）、UNION（并）、EXCEPT（差）。默认都用集合语义（自动去重）；写 ALL 才切换成 multiset 语义。这就是"UNION 为什么没有重复行""为什么 COUNT 会重复计"的根源。multiset 用计数函数 λ(t) 描述：λ 为 0 的项也要写出来参与 min/max。

λ(UNION ALL) = λ_X(t) + λ_Y(t) λ(INTERSECT) = min(λ_X(t), λ_Y(t)) λ(EXCEPT) = max(0, λ_X(t) − λ_Y(t)) λ(t) = 元组 t 在结果中出现的次数。前两条是课件原式；第三条按 multiset 差的标准定义补全（课件只画了集合版）。

算一遍（课件原例）：λ_X = {(1,a):2, (1,b):0, (2,c):3, (1,d):0}，λ_Y = {(1,a):5, (1,b):1, (2,c):2, (1,d):2}。则交 = {2, 0, 2, 0}；并（ALL）= {7, 1, 5, 2}；差 = {0, 0, 1, 0}。注意 (1,b) 在 X 中 count 为 0 但 Y 中为 1，所以并里它是 1、交里是 0。

INTERSECT 的经典错误（必考）

题目："找出在美国和中国都设厂的公司的总部城市"。初学者写：

SELECT hq_city FROM Company, Product
WHERE maker = name AND factory_loc = 'US'
INTERSECT
SELECT hq_city FROM Company, Product
WHERE maker = name AND factory_loc = 'China'

课件反例：X Co. 总部 Seattle 只有美国厂；Y Inc. 总部也在 Seattle 只有中国厂。没有任何一家公司"两国都有厂"，可两个子查询都返回 'Seattle'，交集就把它留下了——因为INTERSECT 做在了 hq_city 上，而条件其实是关于 company 的。正确做法是把两个条件约束到同一个公司上：

SELECT DISTINCT hq_city
FROM   Company, Product
WHERE  maker = name
  AND  name IN (SELECT maker FROM Product
                WHERE factory_loc = 'US')
  AND  name IN (SELECT maker FROM Product
                WHERE factory_loc = 'China')

这里 DISTINCT 不能省：没有它，每匹配一条 Product 元组就输出一次 hq_city（multiset 放大重复）。

再补一个常考对比：UNION 与 UNION ALL 的差别只在重复——UNION 去重，UNION ALL 保留全部。课外补充：去重必须先排序/建哈希，所以 UNION ALL 通常比 UNION 快；已知两个结果集不重叠（如按年份切分）时应该用 ALL。答题时若被问"哪个更快、为什么"，答"UNION ALL 省掉了去重开销"。

INTERSECT / EXCEPT 并非所有 DBMS 都支持，所以常问"怎么改写"：INTERSECT → EXISTS (...) 或 JOIN；EXCEPT → NOT EXISTS (...) 或反连接 LEFT JOIN ... WHERE 右表 key IS NULL（前提：R、S 各自无重复）。

核心概念 5：嵌套查询、相关子查询与量词

为什么能嵌套：SQL 是组合式（compositional）的——一切输入输出都表示为 multiset，一个查询的输出能直接当另一个的输入。子查询返回的就是一张关系表，因此可接 IN / ANY / ALL / EXISTS。

四个常用形式

  • IN：值出现在子查询结果里。WHERE name IN (SELECT maker FROM Product WHERE factory_loc='US')。
  • s > ALL R：比 R 里每一个都大。例 WHERE price > ALL (SELECT price FROM Product WHERE maker='Gizmo-Works') = 比 Gizmo-Works 所有产品都贵。课外补充：ANY/ALL 在 SQLite 中不支持，若题目指定 SQLite 要改用 MAX/MIN 子查询。
  • s < ANY R：比 R 里至少一个大（等价于 s < MAX(R)）。
  • EXISTS R：R 非空即为真。用来找"copycat 产品"：外层 p1 是 Gizmo-Works 的产品，内层找同名但 maker 不同的产品（p1.name = p2.name 引用外层变量 → 这就是相关子查询）。

存在量词容易、全称量词难（课件原话）

存在量词（existential，"there exists"）很容易写：找"至少有一个产品价格 < 100 的公司"，直接 join + 过滤即可。而全称量词（universal，"for all"）很难：找"所有产品价格都 < 100 的公司"，标准做法是双重否定——不存在任何一个价格 ≥ 100 的产品属于它：

SELECT DISTINCT Company.name
FROM   Company
WHERE  Company.name NOT IN (
         SELECT company FROM Product
         WHERE price >= 100)

例：NOT EXISTS (SELECT * FROM Product WHERE company = c.name AND price >= 100) 与上面的 NOT IN 等价，但 NOT IN 在子查询结果含 NULL 时会失效（见易错点），所以考试写 NOT EXISTS 更稳。

这类 "for all" 题是半期最典型的"想不出就写不出"的题，记住模板：∀ 条件 ≡ ¬∃ 反例——把"全部满足"翻译成"不存在不满足的"。

嵌套 IN 与多表 join 是否等价？

课件 p68 的对比：多表版 FROM Company c, Product pr, Purchase p WHERE c.name = pr.maker AND pr.name = p.product AND p.buyer = 'Joe Blow'；嵌套版 WHERE c.name IN (SELECT pr.maker FROM Purchase p, Product pr WHERE p.product = pr.name AND p.buyer = 'Joe Blow')。不写 DISTINCT 时两者行数不同：多表版每条匹配的购买记录输出一行（一个城市可能重复很多次），嵌套版每个 company 只输出一行（IN 只是存在性判断，不放大）。两边都加 DISTINCT 后才等价——课件原话就是 "Beware of duplicates"。

相关子查询（correlated subquery）

内层引用外层变量，因此外层每行都要重跑一次内层。课件两例：① 找"标题出现不止一次"的电影：SELECT DISTINCT title FROM Movie m WHERE year <> ANY (SELECT year FROM Movie WHERE title = m.title)——存在同名但年份不同的记录即成立（<> 就是 !=）。② 找"比同厂商 1972 年前所有产品都贵"的产品，内层用 x.maker = y.maker AND y.year < 1972 与外层关联。课件评价：相关子查询"可以非常强大，但也难优化得多"——这就是"能写但别滥用"的标准考点。

GROUP BY vs 嵌套查询（同一题的两种写法）

题目：找写过至少 10 篇文档的作者（Author(login,name)、Wrote(login,url)）。

-- novice：聚合写在 WHERE 里，语义错误且极低效
SELECT DISTINCT Author.name FROM Author
WHERE COUNT(SELECT Wrote.url FROM Wrote
    WHERE Author.login = Wrote.login) > 10

-- expert：GROUP BY + HAVING
SELECT   Author.name
FROM     Author, Wrote
WHERE    Author.login = Wrote.login
GROUP BY Author.name
HAVING   COUNT(Wrote.url) > 10

三点结论：① 聚合条件必须放 HAVING，不能放 WHERE；② GROUP BY 已保证每组一行，不需要 DISTINCT；③ 嵌套版要对每个作者各跑一次全表扫描，GROUP BY 版只扫一遍，效率高得多。

核心概念 6：聚合、GROUP BY 与 HAVING

五个聚合：SUM / COUNT / MIN / MAX / AVG。除 COUNT 外都作用于单个属性，COUNT(*) 数所有行。COUNT 默认计入重复：COUNT(category) 不去重（该列非空时等价于 COUNT(*)），要不同值必须写 COUNT(DISTINCT category)。课件说 COUNT(category) 与 COUNT(*) 相同，前提正是该列 NOT NULL；若该列可空，两者结果不同：COUNT(*) 数所有行，COUNT(col) 跳过 NULL 行。

SELECT S FROM R1,…,Rn WHERE C1 GROUP BY a1,…,ak HAVING C2 规则：S 只能含分组属性 a1…ak 和/或聚合；C1 只涉及原表属性（WHERE 管单行）；C2 才能涉及聚合（HAVING 管整组）。

语义四步（背下来就能手算任何 GROUP BY 题）：① 算 FROM-WHERE，按 C1 过滤元组；② 按 a1…ak 分组；③ 对每组应用 C2（可用聚合）；④ 算 S 里的聚合，每组输出一行。

手算例（课件原例，务必能复现）

Purchase(product, date, price, quantity) 四行：bagel 10/21 单价 1 数量 20；bagel 10/25 单价 1.5 数量 20；banana 10/3 单价 0.5 数量 10；banana 10/10 单价 1 数量 10。查询按 product 求 SUM(price × quantity) AS TotalSales。

  1. FROM-WHERE：都满足 date > '10/1/2005'，4 行全部保留。
  2. GROUP BY product：分成 Bagel、Banana 两组。
  3. 组内算 SUM(price×quantity)：Bagel = 1×20 + 1.5×20 = 50；Banana = 0.5×10 + 1×10 = 15。
  4. 每组输出一行：(Bagel, 50)、(Banana, 15)。

若再加 HAVING SUM(quantity) > 30：Bagel 的数量和 40 保留，Banana 的 20 被过滤 → 只剩 Bagel 一行。这是"WHERE 先过滤行、HAVING 后过滤组"的最好例子。

为什么 SELECT 不能随便写非分组列：一个组里会有多个不同值，数据库无法决定输出哪个（标准 SQL 直接报错；MySQL 宽松模式会随机取值，这正是坑）。

核心概念 7：NULL 的三值逻辑与外连接

NULL 是什么

NULL 表示"不知道值"，至少涵盖三种语义：值不存在、值存在但未知、值不适用。schema 规定每列能否为空，可用 NOT NULL 约束（如 Students.name）。数值运算有传染性：x 是 NULL 时，4*(3−x)/7 仍是 NULL；而 x = 'Joe' 的结果不是 FALSE，是 UNKNOWN。

FALSE = 0 UNKNOWN = 0.5 TRUE = 1 C1 AND C2 = min(C1, C2) C1 OR C2 = max(C1, C2) NOT C1 = 1 − C1 WHERE 只保留条件结果为 TRUE（1）的元组；结果为 0.5 的行一律丢掉。这是所有 NULL 坑的唯一根源。

两个必须会的坑

① WHERE (age < 25) AND (height > 6 AND weight > 190) 不返回 height 为 NULL 的行：0.5 与其它值取 min 后 ≤ 0.5，不是 1。② WHERE age < 25 OR age >= 25 看似覆盖全部，同样漏掉 age 为 NULL 的行：0.5 与 0.5 取 max 仍是 0.5。修法只有一个——显式判断：WHERE age < 25 OR age >= 25 OR age IS NULL；并用 IS NULL / IS NOT NULL，不能写 x = NULL（NULL = NULL 结果是 UNKNOWN）。

例：Students 表 Jim 的 gpa 为 NULL，则 WHERE gpa >= 3.0 OR gpa < 3.0 不会返回 Jim。

INNER JOIN 丢数据 → OUTER JOIN 补回来

默认的 join（逗号写法、JOIN ON、INNER JOIN ON 三种等价）是 inner join：只保留两边都匹配的组合。所以"从未售出的产品"在 Product JOIN Purchase ON Product.name = Purchase.prodName 里直接消失。外连接把没匹配的一侧用 NULL 补上：

  • LEFT OUTER JOIN：保留左表所有元组，右表没匹配的填 NULL（未售出的 OneClick → 输出 (OneClick, NULL)）。
  • RIGHT OUTER JOIN：保留右表所有元组，左表缺的填 NULL。
  • FULL OUTER JOIN：两侧都保留，各自缺的填 NULL。

外连接两个经典用途：① 找"没有…的"（反连接）LEFT JOIN ... WHERE 右表.key IS NULL，等价于 NOT EXISTS；② 把 EXCEPT 改写成不依赖该运算符的查询（课件 p74 给的正是这个技巧）。

注意外连接补出来的 NULL 表示的是"没有匹配"（不适用），与前面说的"值未知"不是一回事——这正是反连接能用 WHERE 右表.key IS NULL 判定的原因：真值来自"这一侧本来就没有行"，而不是"有行但值是 NULL"。

四种 join 的保留规则
类型保留什么不匹配时典型用途
INNER JOIN只保留两边都匹配的组合整行丢弃常规关联查询
LEFT OUTER左表全部 + 匹配的右表右表列填 NULL保留主表全量（含未售出商品）
RIGHT OUTER右表全部 + 匹配的左表左表列填 NULL与 LEFT 镜像（换表顺序即等价）
FULL OUTER两边全部两侧缺的都填 NULL对账/合并两套名单

⚠ 易错点 / 命题陷阱

  • WHERE 里漏写连接条件：FROM A, B 只在 WHERE 写过滤条件 → 结果是 |A|×|B| 的笛卡尔积。看到行数"莫名等于两表行数相乘"就查这里。
  • OUTER JOIN 把过滤条件从 ON 挪到 WHERE：LEFT JOIN Purchase ON ... WHERE Purchase.store = 'Wiz' 会把 NULL 行（未售出产品）全部删掉，外连接退化成内连接。右表的条件要放 ON 里。
  • NOT IN 遇到 NULL：若子查询结果含 NULL，x NOT IN (...) 变成 UNKNOWN，一行都不返回。课外补充：这是三值逻辑的直接后果，课件未点名但极常考；改用 NOT EXISTS 或先过滤 NULL。
  • COUNT 被 join 放大：先 join 再 COUNT(*) 得到的是连接后的行数，不是实体数（一个作者 10 篇文档会算成 10 行）。要么 COUNT(DISTINCT x)，要么改用 GROUP BY。
  • 集合运算默认去重：UNION 去掉重复、INTERSECT 默认去重，只有 UNION ALL 保留；问"结果几行"时必须先看清有没有 ALL 和 DISTINCT。

🧠 随堂自测

Q1 计算：R(A) = {1, 3}，S(B,C) = {(2,3), (3,4), (3,5)}。求 SELECT R.A FROM R, S WHERE R.A = S.B 的结果行数与内容；加上 DISTINCT 后呢？若 S 为空表呢？

答案：2 行，值是 3、3；加 DISTINCT 后 1 行（值 3）；S 为空则 0 行。

步骤：先笛卡尔积得 2×3 = 6 行组合；再按 R.A = S.B 过滤 —— (1, (2,3)) 1≠2 淘汰，(1,(3,4)) 淘汰，(1,(3,5)) 淘汰，(3,(2,3)) 淘汰，(3,(3,4)) 保留，(3,(3,5)) 保留；最后投影只剩 A 列 → 输出 (3)、(3) 两行（multiset 不去重）。

S 为空时笛卡尔积为空，所以结果为空——这正是课件那道"R, S, T 三表 OR 查询"陷阱的同一原理。

Q2 计算：沿用课件 Purchase 表（bagel 1×20、bagel 1.5×20、banana 0.5×10、banana 1×10）。写 SELECT product, COUNT(*), SUM(price*quantity), SUM(quantity) FROM Purchase GROUP BY product HAVING SUM(quantity) >= 30，输出哪几行？

答案：只有 Bagel 一行：(Bagel, 2, 50, 40)。

Bagel 组：COUNT(*)=2，SUM=1×20+1.5×20=50，SUM(quantity)=40 ≥ 30 → 保留。
Banana 组：COUNT(*)=2，SUM=0.5×10+1×10=15，SUM(quantity)=20 < 30 → 被 HAVING 过滤。

关键顺序：WHERE 先筛行 → GROUP BY 分组 → HAVING 筛组 → SELECT 算聚合。把 HAVING 写成 WHERE SUM(quantity)>=30 是语法错误。

Q3 三值逻辑：Person(age) 里有 age = 20、30、NULL 三行。WHERE age < 25 OR age >= 25 返回几行？为什么？怎么修？

答案：只返回 2 行（20 与 30），NULL 行被漏掉。

推导：age = NULL 时两个条件都是 UNKNOWN = 0.5，OR 取 max(0.5, 0.5) = 0.5，而 WHERE 只保留结果为 1（TRUE）的元组 → 丢弃。

修法：WHERE age < 25 OR age >= 25 OR age IS NULL。注意不能写 age = NULL（结果仍是 UNKNOWN），必须用 IS NULL。

Q4 写查询：找"从未被购买过的产品名"，给出两种写法并说明各自适用场景。

答案：写法一（NOT EXISTS）：SELECT name FROM Product p WHERE NOT EXISTS (SELECT * FROM Purchase WHERE prodName = p.name)；写法二（反连接）：SELECT p.name FROM Product p LEFT JOIN Purchase ON p.name = prodName WHERE prodName IS NULL。

适用：NOT EXISTS 在含 NULL 的表上更安全（不受 NOT IN 的 NULL 陷阱影响）；反连接在多数优化器里更快、也用于改写 EXCEPT。若题目问"为什么不能写 NOT IN"，答：子查询里一旦有 NULL，NOT IN 整个结果变成 UNKNOWN，返回空集。

记忆口诀：SFW 三行（SELECT-FROM-WHERE）；join = 积→筛→投；默认集合去重，写 ALL 才保留重复；聚合四步（过滤→分组→HAVING→算）；NULL 记 0/0.5/1，AND 取 min、OR 取 max、NOT 用 1 减；外连接的条件放 ON，找缺失用 LEFT JOIN + IS NULL。

P7

SQL 是什么语言

考点

这页给 SQL 下定义：它是用于查询和操作数据的标准语言，而且是高级语言（very high-level）——你只描述「要什么」，具体怎么执行由数据库优化器决定，所以「优化得好」是它能成立的前提。标准有很多版本：ANSI SQL、SQL92（SQL2）、SQL99（SQL3），各家厂商只支持其中一部分子集。课件还调侃它是「世界上最成功的并行编程语言」，因为一条查询天然可以拆到多核上跑。SQL = Structured Query Language。

🎯 会问 SQL 是声明式还是过程式：答声明式（declarative）。

P8

SQL 的两副面孔：DDL 与 DML

考点

这页把 SQL 分成两类用途。DDL（Data Definition Language，数据定义语言）负责定义关系模式：创建、修改、删除表及其属性。DML（Data Manipulation Language，数据操纵语言）负责插入、删除、修改表中的元组（tuple），以及查询一张或多张表。记住分工：改「结构」是 DDL，改「数据内容与读取」是 DML；本讲后面九成篇幅都在讲 DML 里的查询。

🎯 判断题：CREATE TABLE 属于 DDL，SELECT 属于 DML。

P9

表 = 元组的 MULTISET

这页给出全讲最基础的定义：一张关系/表（relation）是元组的 multiset（多重集），属性由 schema 指定，然后说「Let's break this definition down」——接下来四页逐词拆解。看页面的 Product 表：4 行数据，列为 PName、Price、Manufacturer，值形如 Gizmo / 19.99 / GizmoWorks。这三个词是重点：元组是行、属性是列、multiset 表示允许完全相同的两行同时存在。

P10

multiset 到底是什么意思

考点

继续拆定义：multiset 是无序列表，也就是允许重复实例的集合。课件用三行对比：List（列表）[1, 1, 2, 3]、Set（集合）{1, 2, 3}、Multiset {1, 1, 2, 3}——multiset 保留重复但不保留顺序。课件还补一句「没有 next() 之类的方法」，意思是表里的行没有「第几行」的概念，天然无序；这正是后面排序要写 ORDER BY、去重要写 DISTINCT 的根本原因。

🎯 「表有顺序」是错的：行无序，要顺序必须 ORDER BY。

P11

属性（列）与原子类型

考点

拆到第二个词：attribute（属性/列）是每个元组里都存在的一个有类型（typed）的数据项。课件特别加了一条 NB：标准 SQL 里属性必须是原子类型（atomic type），不能是列表、集合这类复合值。这条规定直接决定了关系表是「平的（flat）」——没有嵌套表格，也不允许一格塞进一个数组。所以「一张表里存一张子表」在标准 SQL 里做不到，要拆成两张表再加外键。

🎯 「某列可以存数组」在标准 SQL 里是错的（原子性要求）。

P12

元组（行 / record）

拆到第三个词：tuple（元组/行）是表里的一条完整记录，它的各列取值都符合 schema 规定的属性。课件补一句它有时也被叫作 record（记录）。看 Product 表，一行就是「Gizmo, 19.99, GizmoWorks」这一组值。要建立的直觉是：整张表就是一堆这样的行堆起来，行与行之间没有先后，也没有「指针」可以顺着走，所以任何「第几行」的想法都要换成条件筛选或排序。

P13

cardinality 与 arity

考点

拆到最后一对词，也是最容易混的：cardinality（基数）= 元组的个数，即表有几行；arity（元数）= 属性的个数，即表有几列。用页面的 Product 表：四行 → cardinality = 4；PName、Price、Manufacturer 三列 → arity = 3。这两个英文词考试会直接出现，千万别把 cardinality 记成列数。记法：cardinality 更长，对应更「大」的行数；arity 更短，对应列数。

🎯 会考英文术语：行数=cardinality，列数=arity。

P14

SQL 的数据类型

考点

这页列数据类型：字符型 CHAR(20)、VARCHAR(50)；数字型 INT、BIGINT、SMALLINT、FLOAT；其它如 MONEY、DATETIME。核心结论只有两句：每个属性都必须有原子类型，所以表是平的（flat）。CHAR 是定长字符串、VARCHAR 是变长字符串（长度上限写在括号里），这是常见的对比考点；建表时括号里写多少，决定这一列最多能存多长的内容。

🎯 CHAR 定长 vs VARCHAR 变长，是经典选择题。

P15

表的 schema 与键的下划线记法

这页定义 schema：一张表的 schema 由表名、属性名和各自类型组成，写作 Product(Pname: string, Price: float, Category: string, Manufacturer: string)。同时引入 key（键）：取值唯一的属性，书写时给它加下划线。也就是说 schema 里带下划线的属性就是这张表的主键。读题时看到下划线要立刻意识到「这一列不允许重复」，看到两张表之间的同名列就要想到外键。

P16

键是一种隐式约束

考点

这页把键讲成「约束（constraint）」而不是「性质」：键约束限制了哪些元组可以出现在关系里——如果两个元组在键上的取值相同，那它们必须是同一个元组。课件同时给了更精确的定义：key 是属性的最小子集，能充当元组的唯一标识符。两个关键词都不能漏：「子集」说明键可以由多列组成，「最小」说明不能多加一列凑数，例如 (sid, name) 虽然唯一但 name 多余，所以不是键。

🎯 定义要背「最小子集 + 唯一标识」，漏「最小」会扣分。

P17

三问键：选谁、是否必有、能否多个

考点

这页是问答页，三个问题都值得背。以 Students(sid, name, gpa) 为例：① 选谁当键？选 sid，因为学号对每个学生唯一、且不随时间变化。② 键一定存在吗？不一定，键必须在建表时显式声明（primary key），不声明就没有，即使某列天然唯一。③ 能有多个键吗？能：primary key 只有一个；其它也能唯一标识的列叫 candidate key（候选键）；还可以加多个 unique 约束。若 sid 与 email 都唯一，二者都是候选键，但只能选一个当主键。

🎯 「一个表能有两个 primary key」是错的；candidate key 可以多个。

P18

NULL 与 NOT NULL

考点

这页引入空值：想表达「这个值我不知道」就用 NULL，课件老实承认它的语义「有时很痛苦」，后面专门有一节讲。例子里 Students 表有 123 Bob 3.9 与 143 Jim NULL——Jim 刚入学、还没有 gpa，所以填 NULL。同时可以对某列加 NOT NULL 约束，例如这张表的 name 不允许为空。于是列被分成「可空（nullable）」与「不可空」两种，在建表时就定下来。

🎯 NULL 不等于 0、也不等于空字符串，它表示「未知/不存在」。

P19

一般约束与性能代价

考点

这页说 SQL 其实允许写任意断言（arbitrary assertions），例如「数据库课上不能有 25 个人」。但实践中很少这么写，原因只有一个：性能。课件给了一句很值钱的总结：每当我们做丑陋的事（或者避开方便的事），都是为了性能——约束越自由，每次插入或修改都要检查，代价越高。所以工程上常用主键、外键、NOT NULL 这类「便宜又够用」的约束，复杂业务规则放到应用层去保证。

🎯 问「为什么不多写复杂约束」，答：插入/更新时检查代价高。

P20

schema 与约束的总结

考点

小结页，两个要点。① schema（表、列、类型）与各类约束（constraints）是数据库理解数据语义（meaning）的方式，同时也有利于优化（optimization）——优化器知道主键唯一，就能选更快的执行计划。② SQL 支持的通用约束有三种：Primary Key（唯一标识每一行）、Unique Key（保证某列或列组合取值唯一）、Foreign Key（保证一张表里的值指向另一张表或本表中已存在的值）。

🎯 约束有两个作用：表达语义 + 帮助优化，答简答要写全。

P21

第 2 节：单表查询

小章节页：从这里开始真正写查询，但只查一张表。下面依次是 SFW 基本形式、Selection（筛行）、Projection（选列）、输入与输出 schema 的记法、几个易错细节（大小写与引号）、LIKE 模式匹配、DISTINCT 去重、ORDER BY 排序。这一节是后面所有复杂查询的语法底座，写不熟的话，多表、嵌套、聚合都会跟着错。

P22

SFW：SQL 查询的基本形式

考点

这页给出最基本的查询形式，课件叫它 SFW query：SELECT 属性 FROM 表 WHERE 条件。虽然真正的 SQL 还有很多花哨的扩展，但九成查询的骨架就是这三行。理解方式：FROM 决定数据从哪里来，WHERE 决定留下哪些行，SELECT 决定输出哪些列。记住这个顺序，后面学聚合与分组时才知道每一部分在哪一步生效。

🎯 SFW = SELECT-FROM-WHERE，三行骨架必须能默写。

P23

Selection：按条件筛行

考点

第一个操作：Selection（选择）——按条件过滤关系的元组。查询是 SELECT * FROM Product WHERE Category = 'Gadgets'：星号表示保留所有列，WHERE 只留下 Category 等于 Gadgets 的行。对照右侧结果表：原表 4 行是 Gizmo、Powergizmo、SingleTouch、MultiTouch，结果只剩 2 行，正好是两个 Gadgets 商品。要点：Selection 只删行、不删列，输出就是原表的一个子集，换句话说筛完之后行变少、列完全不变。

🎯 选择（selection）筛行、投影（projection）选列，别搞反。

P24

Projection：只保留一部分列

考点

第二个操作：Projection（投影）——输出表只保留原来属性的一部分。查询 SELECT Pname, Price, Manufacturer FROM Product WHERE Category = 'Gadgets'：先按 Category 筛出两行，再把 Category 这一列丢掉，输出只剩 PName、Price、Manufacturer 三列、两行。对照左右两张表，可以直观看到「列少了、行没变」。注意投影默认不去重，即使投影后出现完全相同的行也照样保留。

🎯 投影不去重；去掉重复行必须显式写 DISTINCT。

P25

输入 schema 与输出 schema

考点

这页讲记法：把一条查询看成「schema 到 schema 的映射」。输入 schema 是 Product(PName, Price, Category, Manufacturer)，输出 schema 是 Answer(PName, Price, Manufacturer)——输出 schema 由 SELECT 列表决定，而不是由原表决定。考试常问「这条查询的输出有几个属性、分别是什么」，本质就是让你写出输出 schema：SELECT 里点了几列，答案就有几个属性。

🎯 输出属性数 = SELECT 列表长度（写星号时等于原表列数）。

P26

大小写与引号：三个细节

考点

这页全是细节题。① SQL 命令大小写不敏感：SELECT、Select、select 完全一样，表名也如此，Product 与 product 相同。② 但值（字符串常量）大小写敏感：'Seattle' 与 'seattle' 是两个不同的值，比较结果可能不同。③ 常量必须用单引号：'abc' 是对的，而双引号在标准 SQL 里表示标识符（列名），所以 Category 等于双引号包裹的 Gadgets 是错的。

🎯 值大小写敏感、命令不敏感；字符串用单引号，双引号是标识符。

P27

LIKE：字符串模式匹配

考点

这页讲 s LIKE p 的字符串模式匹配，模式串里有两个特殊符号：%（百分号）匹配任意长度的字符序列，可以为空；_（下划线）匹配恰好一个字符。课件例子是 SELECT * FROM Products WHERE PName LIKE '%gizmo%'，意思是在 PName 的任意位置出现过 gizmo 就命中，所以 Gizmo 与 Powergizmo 都会被选中；若写成 'Gizmo%' 则只匹配以 Gizmo 开头的值。

🎯 %任意长度、_恰好一个字符，这两个通配符必区分。

P28

DISTINCT：消除重复行

考点

这页对比两条查询。SELECT Category FROM Product 得到 Gadgets、Gadgets、Photography、Household，共 4 行，因为原表有两行属于 Gadgets；加上 DISTINCT 后变成 Gadgets、Photography、Household，共 3 行。结论：DISTINCT 作用于整个 SELECT 列表，只有所有被选中的列都相同时才算重复，所以它必须写在 SELECT 之后、作用于整行而不是某一列；多列时也必须多列全都相同才去重。

🎯 DISTINCT 是对整行去重，不是对某一列去重。

P29

ORDER BY：排序与破平

考点

这页讲排序：ORDER BY Price, PName 表示先按 Price 升序排，Price 相同的再用第二个属性 PName 破平（ties are broken by the second attribute），后面还有属性就继续依次破平。默认是升序（ascending），要降序必须写 DESC，例如 ORDER BY Price DESC。注意排序不改变结果集的内容，只影响呈现顺序——这也正好说明「表本身无序」，想要顺序只能显式指定。

🎯 多列排序：前面的相同才看后面的；降序要写 DESC。

P30

第 3 节：多表查询

小章节页：单表之后进入多表。这一节要解决三件事：外键（怎么声明跨表引用）、join 的语义（笛卡尔积再过滤）、以及元组变量歧义（同名属性到底指哪张表）。它也是后面 INTERSECT、嵌套查询、外连接的入口，因为「把多张表拼起来」是这些高级写法的共同底层动作，拼错了后面全错。

P31

外键约束：只允许正式学生选课

考点

这页引入 foreign key（外键）。场景是 Students(sid, name, gpa) 与 Enrolled(student_id, cid, grade)。先注意 student_id 单独不是键——一个学生选多门课，所以键应该是 (student_id, cid) 这个组合。业务要求只有出现在 Students 里的学生才能选课，于是说 student_id 是引用 Students 的外键。页面表格给了 101 Bob 3.2、123 Mary 3.8 与选课 (123,564,A)、(123,537,A+)，注意 Bob 没有选课记录，说明外键只约束「出现时必须存在」。

🎯 外键本身不是本表的键，可以重复、可以为 NULL。

P32

声明外键的写法

考点

这页给出建表语法，考试会直接考细节：CREATE TABLE Enrolled 里依次写 student_id CHAR(20)、cid CHAR(20)、grade CHAR(10)；然后 PRIMARY KEY (student_id, cid) 声明复合主键；最后 FOREIGN KEY (student_id) REFERENCES Students(sid) 声明外键指向 Students 的 sid 列。注意两点：REFERENCES 后面跟的是「表名(列名)」，只写表名不完整；复合主键要把多列写进同一对括号里，而且这两条约束可以写在同一条建表语句中。

🎯 外键必须写 REFERENCES 表(列)；复合主键用括号把多列写一起。

P33

外键遇上插入与删除

考点

外键不是提示，是约束，所以有两种必考情形。① 往 Enrolled 插入一条记录、但对应学生不在 Students 里：INSERT 被拒绝。② 删除一个学生（Students 里的行）：由 DBA 选策略——禁止删除；级联删掉该生的所有选课记录；或者用 NULL 把引用置空（SQL 允许的第三种做法，要求该列可空，课件说后面才展开）。

🎯 插入孤儿记录会被拒；删父行三选一：拒删／级联／置 NULL。

P34

区分键与外键（Product / Company）

考点

这页让你在一对具体表上标出键与外键。Product 表四行，属性是 PName、Price、Category、Manufacturer；Company 表三行，属性是 CName、StockPrice、Country，取值分别为 GizmoWorks 25 USA、Canon 65 Japan、Hitachi 15 Japan。分析思路：能在本表内唯一标识一行的属性是键，所以 Company 的键是 CName、Product 的键是 PName；而 Product 的 Manufacturer 列存的是公司名，取值必须来自 Company.CName，所以 Manufacturer 是外键，它指向 Company 的主键 CName。

🎯 识别套路：能唯一标识本表的是键；指向别表键的是外键。

P35

Join 入门：日本产、200 美元以下

考点

第一次真正拼两张表。题目：找出日本制造、价格不超过 200 的商品名与价格。写法是 SELECT PName, Price FROM Product, Company WHERE Manufacturer = CName AND Country = 'Japan' AND Price <= 200。注意 WHERE 里混了三类条件：连接条件（Manufacturer = CName，把两表对应起来）、过滤条件（Country 等于 Japan 与价格上限）。课件还提醒：后面为简洁常省略属性类型，但默认都是原子类型。

🎯 FROM 多个表时，WHERE 里必须有连接条件，否则退化成笛卡尔积。

P36

join 的定义

这页给 join 下定义：两表之间的 join 返回它们元组的所有满足连接条件的唯一组合。换句话说，先把 Product 的每一行与 Company 的每一行配对，得到所有组合，再只保留 Manufacturer = CName 且满足其它条件的那些组合。页面把同一段 SQL 再放一遍，是为了让你把「定义」和「代码」对应起来：FROM 后面列两个表 = 产生所有组合，WHERE = 筛选并连接。

P37

join 的两种等价写法

考点

这页展示同一件事的两种写法。① 逗号写法：FROM Product, Company WHERE Manufacturer = CName AND Country = 'Japan' AND Price <= 200。② 显式写法：FROM Product JOIN Company ON Manufacturer = CName AND Country = 'Japan' WHERE Price <= 200。两者等价：JOIN 后面用 ON 给连接条件，也可以顺手写过滤，WHERE 里放剩下的过滤。之所以等价，是因为 join 的语义本来就是「先组合再过滤」，ON 与 WHERE 都在过滤这一步生效；只有外连接时二者才不等价。

🎯 逗号+WHERE 与 JOIN...ON 等价，这是改写题常考的形式。

P38

join 的结果表

考点

这页把上面那条查询的结果画出来，正好用来练手算 join。Product 四行：Gizmo 与 Powergizmo 都属于 GWorks，SingleTouch 属于 Canon，MultiTouch 属于 Hitachi；Company 三行分别对应 USA、Japan、Japan。执行顺序是：先做笛卡尔积得到 4×3 = 12 个组合，再用 Country = Japan 去掉 USA 那批，用价格上限去掉 203 美元那件，最后只剩 SingleTouch 149.99 美元 一行。注意连接条件先决定哪些行能配上，过滤再削减。

🎯 手算套路：笛卡尔积→连接条件→过滤条件→投影，一步不能省。

P39

元组变量歧义：name 指哪张表

考点

问题页。有两张表 Person(name, address, worksfor) 与 Company(name, address)，查询是 SELECT DISTINCT name, address FROM Person, Company WHERE worksfor = name。问：这里的 address 是哪张表的 address，name 又是哪个 name？因为两张表都有 name 与 address，不加限定时数据库无法确定；标准 SQL 要求列名在一条语句内唯一，所以这种写法会产生歧义，多数系统直接报错，即使不报错输出也不可预测。

🎯 两张表有同名列时必须限定表名，否则报歧义错误。

P40

两种消除歧义的写法

考点

接上页给两种解法。① 用表名限定：SELECT DISTINCT Person.name, Person.address FROM Person, Company WHERE Person.worksfor = Company.name。② 用别名（tuple variable，元组变量）：FROM Person p, Company c WHERE p.worksfor = c.name。两种完全等价，课件明确写 both equivalent。建议一律用第二种：复杂查询里表名很长，别名更清爽，而且后面相关子查询必须靠别名区分内外层的同名表，所以这两种写法都要会认。

🎯 相关子查询必须靠别名区分内外层同名表，别名要练熟。

P41

SQL 语义：嵌套循环

考点

这页把查询的语义（semantics）写成伪代码，是理解一切反直觉查询的钥匙。写法是 SELECT 若干属性 FROM R1 AS x1, …, Rn AS xn WHERE 条件，语义等价于：先让 Answer 为空，再对 x1 遍历 R1、x2 遍历 R2……逐层循环，每取一组变量就检查条件，满足就把这组取值拼成元组加入 Answer。课件强调两点：这是多重集并（multiset union），不去重；而且它几乎从不是最快的算法，只是「意思」。

🎯 「语义」≠「执行顺序」：这页讲含义，不是数据库真正跑法。

P42

语义示例：三行的小表

考点

这页用具体例子把上页伪代码走一遍。R(A) 只有两行：1 和 3；S(B,C) 有三行：(2,3)、(3,4)、(3,5)。第一步笛卡尔积：2×3 = 6 行组合。第二步按 R.A = S.B 筛选：只有 R.A = 3 能与 S.B = 3 的两行配上，所以剩 (3,(3,4)) 与 (3,(3,5))。第三步投影只留 A 列，输出两个 3。注意结果是 3、3 两行——没有去重，这正好演示了 multiset 语义。

🎯 手算牢记三步：笛卡尔积→条件筛选→投影；行数最容易算错。

P43

join 的三步公式

考点

这页把 join 的三步语义写成式子，并强调顺序。① 取笛卡尔积 X = R × S；② 施加选择条件，得到 Y = { (r,s) ∈ X | r.A = s.B }；③ 投影 Z = 只保留 A 列。课件还给了笛卡尔积的直观例子：{a,b,c} × {1,2} 得到 (a,1)、(a,2)、(b,1)、(b,2)、(c,1)、(c,2) 六个组合。结论一句话：join 就是笛卡尔积再做过滤，而投影只是「返回部分属性」。

🎯 记住：join = 笛卡尔积 + 过滤；投影 = 选列。

P44

语义不等于执行顺序

考点

短页，但概念很关键：前面几页展示的是 join 的语义（semantics），也就是「结果应该是什么」；而不是数据库引擎在底层真正的执行方式（execution order）。真实 DBMS 绝不会傻乎乎地物化整个笛卡尔积，它会用索引、哈希连接、排序合并等策略得到同样的结果。所以做题时用语义推答案，估性能时另算，两件事不要混。

🎯 考「数据库是否真做笛卡尔积」：否，那只是语义解释。

P45

小陷阱：哪些国家产 Gadgets

考点

这页是道小陷阱题：找出生产 Gadgets 类产品的国家。写法是 SELECT Country FROM Product, Company WHERE Manufacturer = CName AND Category = 'Gadgets'。看起来没问题——把两张表按厂商连起来，再筛类目。但请先自己数一数：GWorks 有几件 Gadgets 商品？答案是两件（Gizmo 与 Powergizmo），所以 USA 会被输出两次。下一页揭晓结果与解法，先自己动笔数一遍再翻页。

🎯 先别翻页：数一数 GWorks 有几件 Gadgets 商品。

P46

重复行的问题与 DISTINCT

考点

结果揭晓：Product 表里 GWorks 有两件 Gadgets（Gizmo 19 美元、Powergizmo 29 美元），所以连接后 USA 出现两次；而 Canon 与 Hitachi 没有 Gadgets 产品，不会出现。于是输出是 USA、USA 两行，问题就是重复。解法是加 DISTINCT：SELECT DISTINCT Country，输出只剩一个 USA。这也解释了课件为什么反复强调表是 multiset——连接会按匹配次数放大行数。

🎯 join 会按匹配次数放大行数；要国家列表就得 DISTINCT。

P47

Part II 章节页

章节页，进入 SQL Part II。Part I 讲完了建表与基本查询（单表、多表），Part II 要讲更高级的写法：集合运算符与嵌套查询、聚合与分组、NULL 的三值逻辑、外连接。这些内容在考试里比重更大，也更爱出「这个查询返回什么」的结果推算题，所以要一页页跟着算。

P48

第 1 节：集合运算与嵌套

小章节页：集合运算符（INTERSECT / UNION / EXCEPT）与嵌套查询。先给一个提醒：这两个话题看起来无关，其实是同一件事的两面——集合运算要求两个查询的「形状」（属性个数与类型）一致，而嵌套查询就是把一个查询的结果当成另一个查询的输入。SQL 之所以能这么做，是因为输入输出都被统一表示成表（multiset）。

P49

反直觉查询：它到底算什么

考点

这页抛出一个反直觉查询，先别急着算结果，问自己它到底算什么：SELECT DISTINCT R.A FROM R, S, T WHERE R.A = S.A OR R.A = T.A。直觉上它像「R 与 S 或 T 在 A 上相交」，也就是 R ∩ (S ∪ T)；但 WHERE 里是 OR，数据来源却是三张表的笛卡尔积。下一页会揭晓：这个直觉在一种特殊情况下会彻底失效。

🎯 先想：为什么这里要写 DISTINCT？

P50

它算 R ∩ (S ∪ T)，但如果 S 空

考点

这页给出部分答案：这条查询算的是 R ∩ (S ∪ T)，也就是「A 值既出现在 R，又出现在 S 或 T 里」的那些 R 行。但课件紧接着问：如果 S 是空集呢？注意笛卡尔积里包含 S——只要有一张表是空的，R × S × T 就整体为空，那么无论 OR 的另一边多宽松，结果都会是空集，而不是直觉上的 R ∩ T。

🎯 空表参与笛卡尔积会把整个结果清零，这是最大的坑。

P51

回到语义：S 为空则结果为空

考点

揭晓答案：如果 S = {}，那么 R、S、T 的笛卡尔积就是空集，后面的选择条件无从作用，最终结果也是空集。所以这条查询并不总能算出 R ∩ (S ∪ T)，它只在 S 非空时才碰巧正确。课件给的教训是：遇到看不懂的查询，就回到语义——笛卡尔积、筛选、投影——一步步推，不要凭符号形状猜结果。

🎯 记住反例：S 为空时结果为空，不是 R∩(S∪T)。

P52

换成 Python 看语义

这页换个视角：用 Python 把同样的语义写出来。语义三步（笛卡尔积、选择、投影）翻译成程序就是三层嵌套的 for 循环——最外层遍历 R，中间遍历 S，内层遍历 T；连接与笛卡尔积本质上就是「嵌套循环」，而条件就是循环里的 if 语句。课件说这是最简单的实现方式。这样看，查询结果的规模也很好估：循环总次数 = 三张表行数的乘积。

P53

Python 代码与 S 空的问题

考点

这页给出完整代码：output 初始化为空集合，三层 for 循环遍历 r、s、t，只要 r 的 A 等于 s 的 A 或等于 t 的 A，就把 r 的 A 加进输出，最后返回列表。然后课件问：现在你能看出 S 是空列表时会发生什么吗？答案是——for s in S 一次都不执行，于是内层循环体（包括那个判断）根本不会跑，output 始终为空。这就是上页结论的程序版解释。

🎯 空集合会让循环体一次都不执行，这是编程视角的解释。

P54

小节页：MULTISET 运算

小章节页：把集合运算推广到多重集（multiset）运算。前面的 INTERSECT、UNION 默认都是集合语义（自动去重），可 SQL 的表是 multiset，所以必须回答一个新问题：重复出现的行在交、并、差里各算几次？接下来先复习 multiset 的计数记法，再给出三种运算的计数规则，最后回到 SQL 的 INTERSECT、UNION、EXCEPT 与 ALL 关键字。

P55

复习 MULTISET 的计数记法

考点

复习 multiset 的表示法：用 λ_X(t) 表示元组 t 在多重集 X 中出现的次数。页面例子：X 里 (1,a) 出现 2 次、(1,b) 出现 1 次、(2,c) 出现 3 次、(1,d) 出现 2 次，等价于把它写成一列重复的元组。注意两条约定：集合里所有计数只能是 0 或 1；没被列出的元组其计数隐含为 0，写公式时要把它当 0 参与运算。

🎯 λ 是「出现次数」；没列出的元组计数按 0 处理，别漏。

P56

多重集的交：计数取 min

考点

这页把上一页的计数记法用到交（intersection）上：多重集的交，每个元组的计数取两边计数的最小值，即 λ_Z = min(λ_X, λ_Y)。对照页面表格：X 的四个元组计数是 2、0、3、0，Y 是 5、1、2、2，于是 Z 是 2、0、2、0。注意 (1,b) 在 X 里是 0、在 Y 里是 1，取 min 后仍是 0——只在一侧出现的元组进不了交集。若换成普通集合，这个公式就退化成熟悉的交集。

🎯 交集的计数取 min；一侧没有的元组结果必为 0。

P57

多重集的并：计数相加

考点

接着看并（union）：多重集的并，计数直接相加，即 λ_Z = λ_X + λ_Y。同样四组数据：X 是 2、0、3、0，Y 是 5、1、2、2，相加得 7、1、5、2，与页面表格完全一致。这里特意保留了计数为 0 的项，因为 0 加上对方的计数仍然有意义。对普通集合它是并集，对 multiset 就是「把所有副本倒在一起」，所以并完的行数等于两张表行数之和。

🎯 并的计数相加；UNION ALL 用的就是这个公式。

P58

小节页：SQL 里的 MULTISET 运算

小章节页：把上两页的计数公式落回 SQL 语法。SQL 用关键字区分两种语义：默认（不写 ALL）是集合语义，自动去重；写了 ALL 才是多重集语义，保留重复并做计数运算。接下来依次给出 INTERSECT、UNION、UNION ALL、EXCEPT 四个例子。注意一个语法前提：运算符前后两个查询的属性个数与类型必须一致，否则无法比较。

P59

INTERSECT：交

考点

第一个集合运算符是 INTERSECT（交）。页面给两个查询：Q1 是 SELECT R.A FROM R, S WHERE R.A = S.A，Q2 是 SELECT R.A FROM R, T WHERE R.A = T.A，中间用 INTERSECT 连起来。语义上就是先分别算出两个结果集，再取交集。注意每个子查询内部还在做 join（R 与 S、R 与 T），所以容易看晕：建议先把 Q1、Q2 的结果各算出来，再求交。默认集合语义，交完自动去重。

🎯 先把两个子查询各算一遍，再求交/并/差，别一眼扫。

P60

UNION：并为什没有重复

考点

第二个是 UNION（并）：Q1 UNION Q2 会把两个结果集合并。课件在这里问：为什么结果里没有重复行？因为 默认 SQL 使用集合语义，UNION 会自动去重。紧接着又问：如果我们偏要重复呢？这就引出下一页的 UNION ALL。记忆点一句话：UNION 是并集（去重），UNION ALL 是多重集并（保留重复）。

🎯 UNION 默认去重；要保留重复必须写 UNION ALL。

P61

UNION ALL：保留重复

考点

这页讲 UNION ALL，区别只在 ALL 表示多重集运算。结果里同一行出现几次就保留几次：若某个值在 Q1 出现 2 次、在 Q2 出现 3 次，UNION 只留 1 行，UNION ALL 留 5 行——这正是 p57 那条 λ_Z = λ_X + λ_Y 的公式。考试常问「两个查询 union 后一共几行」，一定要先看有没有 ALL，再看有没有 DISTINCT。

🎯 行数题：先确认有没有 ALL 或 DISTINCT，再数重复。

P62

EXCEPT：差

考点

第三个是 EXCEPT（差）：Q1 EXCEPT Q2，结果是在 Q1 中出现、但不在 Q2 中出现的元组。默认同样是集合语义、自动去重。复习时可把它与 NOT EXISTS 对照：EXCEPT 是集合运算，要求两边形状一致；NOT EXISTS 是逐行判断的嵌套查询，两者在表里有重复行时结果可能不同。补充一条：多重集差的计数是 max(0, λ_X − λ_Y)，课件只画了集合版，这条按标准定义补全。

🎯 EXCEPT 是集合差；表有重复行时结果与 NOT EXISTS 不同。

P63

INTERSECT 的经典陷阱

考点

这页是 INTERSECT 的高频陷阱题。表是 Company(name, hq_city) 与 Product(pname, maker, factory_loc)。题目：找出在美国和中国都设厂的公司的总部城市。初学者的写法是：两个子查询各筛一种 factory_loc，再把它们的 hq_city 做 INTERSECT。看起来挺合理，但下一页的反例会让你看到：两家不同公司各满足一半条件，也会被错误算成「都满足」。

🎯 先想：INTERSECT 交的是城市，可条件其实关于公司。

P64

反例：两个 Seattle

考点

反例表格给出了 C JOIN P 的结果：X Co. 总部 Seattle，只有美国工厂；Y Inc. 总部也在 Seattle，只有中国工厂。第一个子查询筛 factory_loc = 美国，返回 Seattle（来自 X Co.）；第二个筛中国，也返回 Seattle（来自 Y Inc.）。两个结果集都有 Seattle，于是 INTERSECT 输出 Seattle——但事实上没有任何一家公司同时在美国和中国设厂。

🎯 看表时注意：两个 Seattle 来自不同公司，这才是错误根源。

P65

错因：交错了属性

考点

结论一句话：我们把 INTERSECT 做在了错误的属性上——条件的主体是「公司」（要求同一家公司有两个工厂），交的却是 hq_city（城市）。城市相同不代表公司相同。这类错误的通用诊断法是问自己：两个结果集里的同一行，是不是来自同一个实体？修法在下一页：把两个条件都约束到同一个 name 上。

🎯 错因：交的属性与条件的主体不是同一个东西。

P66

修法：两个 IN 绑到同一家公司

考点

正确写法：外层仍从 Company, Product 取 hq_city，但把两个条件改成两个 IN 子查询，都用 name 关联：name IN (SELECT maker FROM Product WHERE factory_loc = 美国) 并且 name IN (… 中国)。这样两条约束落在同一家公司上。还要注意 DISTINCT：没有它，每匹配一条 Product 记录就输出一次 hq_city（multiset 放大），课件专门问「不加 DISTINCT 会返回几份」。答案就是：每匹配到一条工厂记录，总部城市就会被复制一次。

🎯 两个 IN 都要绑在 name 上；DISTINCT 不能省。

P67

为什么可以嵌套：组合式

考点

这页解释「为什么能嵌套」：SQL 是组合式（compositional）的——所有输入输出都用同一种东西表示，也就是 multiset（表），于是一个查询的输出可以原样当作另一个查询的输入。课件说这一点极其强大：正因为形状统一，才可能有子查询、IN/EXISTS，以及后面视图、派生表这些写法。

🎯 嵌套的前提：输入输出都是表（multiset）。

P68

子查询返回关系：一个例子

考点

一个实际例子：找出「Joe Blow 买过的产品的制造商所在城市」。三张表 Company(name, city)、Product(name, maker)、Purchase(id, product, buyer)。外层查 Company 的 city，条件是 c.name IN 子查询；子查询从 Purchase 与 Product 的连接里取出 maker，条件是 p.product = pr.name 且 p.buyer = 'Joe Blow'。读法建议从内往外：先找 Joe Blow 买了什么，再找谁制造的，最后找公司在哪个城市。注意子查询只返回 maker 这一列，必须与外层的 name 对齐。

🎯 读嵌套查询从内往外读：先算子查询，再算外层。

P69

嵌套版与连接版等价吗

考点

这页问一个关键问题：把上页的嵌套写法改写成三表连接（FROM Company c, Product pr, Purchase p，WHERE 三个等值条件），两个查询等价吗？课件的答案是不等价——因为连接版会按匹配次数产生重复行（一个城市可能出现多次），而嵌套 IN 版每个公司只输出一行。课件提醒一句：Beware of duplicates，小心重复。

🎯 不写 DISTINCT 时两版行数不同，这就是「等价吗」的答案。

P70

都加 DISTINCT 后才等价

考点

这页给结论：两边都加上 DISTINCT 之后，两个查询才真正等价（都用集合语义）。也就是说「嵌套 IN 版」与「三表连接 + DISTINCT 版」可以互相改写，考试常让你在两者之间转换。改写时要检查两件事：属性列表是否一致、是否需要 DISTINCT 消除连接放大出来的重复行。

🎯 改写口诀：加 DISTINCT 后才等价；属性列表要对齐。

P71

量词：ANY 与 ALL

考点

这页进入量词用法：SELECT name FROM Product WHERE price > ALL (SELECT price FROM Product WHERE maker = 'Gizmo-Works')，意思是「比 Gizmo-Works 生产的每一件产品都贵」。三个常用形式：s > ALL R（比 R 中所有值都大）、s < ANY R（比 R 中某个值小，即小于最大值）、EXISTS R（子查询非空即为真）。课件提醒 ANY/ALL 在 SQLite 里不支持，遇到要改写成 MAX/MIN 子查询，例如「大于所有」等价于「大于子查询的最大值」。

🎯 ANY/ALL 在 SQLite 不支持；改写用 MAX/MIN 或 EXISTS。

P72

EXISTS 与相关子查询

考点

EXISTS 的例子：找「山寨产品」——由竞争对手生产、但名字与 Gizmo-Works 产品相同的商品。外层限定 p1.maker = 'Gizmo-Works'，内层 EXISTS 里找 p2：p2.maker 不等于 Gizmo-Works 且 p1.name = p2.name。注意内层引用了外层的 p1，这就是相关子查询（correlated subquery）——外层每一行都要重跑一次内层。课件补一句：不等于在标准 SQL 里写成尖括号形式，很多方言也接受感叹号加等号。

🎯 内层出现外层别名＝相关子查询，外层每行跑一次。

P73

用嵌套替代 INTERSECT / EXCEPT

考点

这页说明嵌套查询可以替代 INTERSECT 与 EXCEPT——因为有些 DBMS 根本不支持这两个运算符。替换法：R 与 S 求交，写成 SELECT … FROM R WHERE EXISTS (SELECT * FROM S WHERE R.A = S.A AND R.B = S.B)；R 减 S，写成 WHERE NOT EXISTS（同样的子查询）。课件还问：如果 R、S 各自没有重复行，能不能不用子查询？下一页给 JOIN 与 LEFT JOIN 的写法。注意替代写法的子查询里要同时约束 A、B 两列，否则语义会变。

🎯 EXISTS 对应交、NOT EXISTS 对应差，这题常考改写。

P74

用 JOIN 替代：交与反连接

考点

答案：可以。求交写作 SELECT R.A, R.B FROM R JOIN S WHERE R.A = S.A AND R.B = S.B，前提是两边都没有重复行，否则还要 DISTINCT。求差写作 SELECT R.A, R.B FROM R LEFT JOIN S ON R.A = S.A AND R.B = S.B WHERE S.A IS NULL——也就是反连接（anti-join）：左连接之后，右表为 NULL 的行就是「在 S 里找不到的 R 行」。这个套路在本讲末尾的外连接一节还会再用一次。用反连接前要确认右表的连接列可以为空，否则判断会失准。

🎯 反连接模板：LEFT JOIN … WHERE 右表的键 IS NULL。

P75

相关查询：同名多部的电影

考点

这页讲相关查询（correlated query）：内层子查询用到了外层的变量。例子是找「标题出现过不止一次」的电影：外层把 Movie 取别名为 m，内层同样查 Movie 的年份，条件是 title = m.title；只要存在一个与外层不同的年份（year 不等于 ANY），就说明这个标题不止一部。课件提醒注意变量作用域（scoping）：内层的 title 默认指内层表，所以必须用 m.title 指外层。

🎯 作用域规则：内层同名列默认指内层，外层要别名限定。

P76

复杂相关查询：同厂商更贵

考点

更复杂的相关查询：找出「比同一厂商 1972 年前所有产品都贵」的产品。外层 x 遍历 Product，内层 y 也遍历 Product，条件是 x.maker = y.maker 且 y.year 在 1972 年之前，再用 x.price > ALL（内层价格）。这样外层每个产品都要跑一次内层。课件评价：相关子查询可以非常强大，但也难优化得多——这正是它常被改写成连接或窗口函数的原因。

🎯 相关子查询强但难优化；能改写成 join 就改写。

P77

基本 SQL 小结

这一段的小结：SQL 是一种高层的声明式语言，用于数据操纵（DML）；最核心的构件是 SFW 块（SELECT-FROM-WHERE）；集合运算符很强大但有不少微妙之处（默认去重、INTERSECT 属性选错会出错）；嵌套查询同样强大，还能替代部分集合运算。接下来进入聚合与分组。

P78

第 2 节：聚合与分组

小章节页：进入聚合与分组（Aggregation & GROUP BY）。前面所有查询都是「一行进一行出」地筛选；从这里开始，输出可以是「一组行汇总成一行」。这一节要掌握四件事：五个聚合函数、GROUP BY 的分组语义、HAVING 与 WHERE 的分工，以及 GROUP BY 与嵌套查询的效率差别。

P79

本节内容清单

本节的内容清单，三块：① 聚合运算符（aggregation operators）——SUM、COUNT、MIN、MAX、AVG；② GROUP BY——按属性分组，每组输出一行；③ GROUP BY 配合 HAVING，以及整个查询的求值语义。带着三个问题往下看：聚合在哪一步算、分组依据是什么、筛选行与筛选组有什么不同。另外要记住：分组之后结果的行数通常远少于原表行数。

P80

五个聚合函数

考点

这页介绍聚合函数：SQL 支持 SUM（求和）、COUNT（计数）、MIN（最小）、MAX（最大）、AVG（平均）。两条示例：SELECT COUNT(*) FROM Product WHERE year > 1995 数出满足条件的行数；SELECT AVG(price) FROM Product WHERE maker = 'Toyota' 求丰田产品的平均价。注意课件的提醒：除 COUNT 之外，所有聚合都作用在单个属性上——SUM、AVG、MIN、MAX 都要指定列，只有 COUNT(*) 是按行数统计。所以写 SUM()、AVG() 时括号里必须给出列名或表达式，留空会直接报错。

🎯 COUNT(*) 数行；其余聚合必须指定一个属性。

P81

COUNT 的重复问题

考点

这页专门讲 COUNT 的重复：COUNT 默认把重复值算进去。所以 SELECT COUNT(category) 与 COUNT(*) 结果相同——课件问 Why？原因是这一列非空，每一行都有一个 category 值。但业务上常想知道「有多少种不同的类目」，那就得写 SELECT COUNT(DISTINCT category)。三句话记牢：COUNT(*) 数行数、COUNT(col) 数该列非空的行数、COUNT(DISTINCT col) 数不同取值的个数。

🎯 COUNT(col) 等于 COUNT(*) 的前提是 col 非空。

P82

SUM 的两个例子

考点

两个对比示例：SELECT SUM(price * quantity) FROM Purchase，与同一句加上 WHERE product = 'bagel'。前者求所有购买记录的总金额（每行先算单价乘数量，再求和），后者只求 bagel 的总金额。课件问「它们分别是什么意思」，就是让你区分「作用于全表」与「先过滤再聚合」。注意 price * quantity 是逐行算出来再累加，不是先分别求和再相乘，这一点常被算错。

🎯 SUM(price*quantity) 是逐行相乘再累加，别算成两个 SUM 相乘。

P83

手算：bagel 的销售额

考点

具体算一遍。Purchase 表四行：bagel 10/21 单价 1 数量 20；banana 10/3 单价 0.5 数量 10；banana 10/10 单价 1 数量 10；bagel 10/25 单价 1.5 数量 20。查询只取 product = 'bagel' 的两行，分别算 1×20 = 20 与 1.5×20 = 30，相加得 50。课件正是这么写的：50 = 1*20 + 1.50*20。这类小题几乎必考，注意别把 banana 的行算进去。若去掉 WHERE 条件，四行全算：1×20 + 0.5×10 + 1×10 + 1.5×20 = 65。这个 50 也正是后面 GROUP BY 例子里 bagel 那一组的结果来源。

🎯 会问「结果是多少」，必须手算并写出算式。

P84

GROUP BY：按商品汇总

考点

这页引入分组聚合：SELECT product, SUM(price * quantity) AS TotalSales FROM Purchase WHERE date > '10/1/2005' GROUP BY product，意思是「统计 2005 年 10 月 1 日之后每个商品的销售额」。关键是 GROUP BY：把行按 product 的取值分组，组内再做聚合，每组只输出一行。所以结果不是 4 行，而是 2 行（bagel 一组、banana 一组）。也正因如此，SELECT 里的 product 必须是分组属性，否则输出哪个值都说不通。

🎯 GROUP BY 后行数等于分组数，不再等于原表行数。

P85

分组聚合的语义三步

考点

这页给出分组聚合的语义，三步：① 先算 FROM 与 WHERE，得到满足条件的行；② 按 GROUP BY 里的属性分组；③ 计算 SELECT 里的分组属性与聚合。顺序很重要：WHERE 在分组之前过滤单行，所以 WHERE 里不能出现聚合；聚合是在分组之后、对每组算的。记住「先筛行、再分组、后聚合」，后面 HAVING 就自然理解了。

🎯 语义顺序：FROM/WHERE → GROUP BY → SELECT（含聚合）。

P86

第一步：FROM 与 WHERE

考点

第一步的图示：FROM Purchase WHERE date > '10/1/2005'，四行数据（bagel 两行、banana 两行）全部满足日期条件，所以都保留。注意这一步完全没有分组、也没有聚合，只是普通的选择（selection）。考试常在这里埋坑：如果 WHERE 把某一组的所有行都过滤掉了，那么这一组整个不会出现在结果里，而不是输出 0。

🎯 某组全被 WHERE 过滤掉时，该组不出现，而不是输出 0。

P87

第二步：GROUP BY 分组

考点

第二步的图示：按 GROUP BY product 把四行分成两组——bagel 组有 10/21 与 10/25 两行，banana 组有 10/3 与 10/10 两行。分组之后，组内行之间不再有先后，可以理解成「每组是一个小袋子」，后面的聚合就在每个小袋子里算。这也能解释为什么 SELECT 里只能写分组属性或聚合：组内其它列有多个取值，数据库无法决定输出哪一个。

🎯 SELECT 只能写分组属性或聚合，否则标准 SQL 报错。

P88

第三步：算聚合出结果

考点

第三步的图示：对每组算 SUM(price*quantity)。bagel 组为 1×20 + 1.5×20 = 50；banana 组为 0.5×10 + 1×10 = 15。结果表只有两行两列（product 与 TotalSales）。三步语义到这里走完；考试手算 GROUP BY 题就按「筛行→分组→组内算聚合」写步骤，把中间结果也写出来，最容易拿满分。顺着这一步再记住：某组没有出现，不代表它的销售额是 0，而是它根本没有出现在结果里。

🎯 结果两行：bagel 50、banana 15，这两个数字要记牢。

P89

HAVING：对组做过滤

考点

这页加入 HAVING：查询变成 … GROUP BY product HAVING SUM(quantity) > 100，意思是「只保留总购买量超过 100 的商品组」。课件点明关键差别：HAVING 里的条件是关于聚合的，而 WHERE 里的条件是关于单个元组的。执行顺序上 WHERE 先（筛行）、HAVING 后（筛组），所以「按组过滤」只能写 HAVING，写进 WHERE 会直接报错。

🎯 WHERE 筛行、HAVING 筛组；聚合条件只能进 HAVING。

P90

分组聚合的通用形式

考点

这页给出通用形式：SELECT S FROM R1, …, Rn WHERE C1 GROUP BY a1, …, ak HAVING C2，并规定三件事。① S 只能包含分组属性 a1…ak 和/或对其余属性的聚合，不能是随便的列；② C1 是作用在原表属性上的条件，即筛单行；③ C2 是作用在聚合表达式上的条件，即筛整组。课件末尾写了个 Why？——因为组内其它列有多个值，输出它们没有唯一答案。

🎯 三个位置各能写什么，是简答题的标准答案。

P91

四步求值顺序

考点

这页把上页形式拆成四步求值：① 求 FROM-WHERE，即对 R1…Rn 应用 C1；② 按 a1…ak 分组；③ 对每组应用 C2（这里可以用聚合）；④ 计算 S 中的聚合并返回。与 p85 的三步对照看，多了 HAVING 这一步，位置在分组之后、输出之前。做题时按这四步逐条写，就不会把 HAVING 和 WHERE 混在一起。

🎯 四步：FROM-WHERE → GROUP BY → HAVING → SELECT 聚合。

P92

新手写法：聚合塞进 WHERE

考点

这页对比两种写法，先看新手版：想找写过至少 10 篇文档的作者，写成 SELECT DISTINCT Author.name FROM Author WHERE COUNT(子查询) > 10。问题有两个：聚合不能写在 WHERE 里（WHERE 阶段还没有分组，谈不上 COUNT）；而且这种写法要对每个作者都跑一遍子查询。课件直接标注 This is SQL by a novice。若考题让你找错，这两点都要指出。

🎯 WHERE 里出现 COUNT 就是错，这是找错题的标准陷阱。

P93

专家写法：GROUP BY + HAVING

考点

专家版：SELECT Author.name FROM Author, Wrote WHERE Author.login = Wrote.login GROUP BY Author.name HAVING COUNT(Wrote.url) > 10。三点改进：① 用 GROUP BY 把每个作者对应的行聚成一组；② 用 HAVING 对组做计数条件；③ 不需要 DISTINCT，因为 GROUP BY 天然保证每组只输出一行。课件标注 This is SQL by an expert——这两种写法的对比几乎必考。补一句：这里 COUNT(Wrote.url) 与 COUNT(*) 结果相同，因为 url 列非空。两版 SQL 都要能默写，并能说出新手版错在哪。

🎯 GROUP BY 自动去重，不需要再写 DISTINCT。

P94

两种写法的效率差别

考点

这页追问效率：第 1 种（嵌套）要对每一个作者各跑一次「扫描整个 Wrote 表」的查询，代价大约是作者数乘以 Wrote 的行数；第 2 种（GROUP BY）只需把两张表连接、分组一次，再对每组计数。结论：用 GROUP BY 通常高效得多。答题模板：遇到「每个…有多少…」的聚合问题，优先 GROUP BY + HAVING，而不是在 WHERE 里塞子查询。

🎯 效率：嵌套版对每个作者重扫一次，GROUP BY 只扫一遍。

P95

第 3 节：进阶 SQL 写法

小章节页：Advanced SQL-izing，讲三个进阶话题：量词（ANY/ALL/IN/EXISTS，尤其是全称量词）、NULL 的三值逻辑，以及内连接与外连接的差别。这三块都是易错区：全称量词要会双重否定，NULL 要会算三值逻辑，外连接要分清 ON 与 WHERE 的位置。这三块内容彼此独立，但都很容易出判断与改错题。

P96

存在量词：容易的那一类

考点

先讲存在量词（existential）：找「至少有一件产品价格低于 100 的公司」。写法很直接：SELECT DISTINCT Company.cname FROM Company, Product WHERE Company.name = Product.company 且价格低于 100。课件评价 existential 很容易——因为「存在」只要找到一个例子就行，用连接加过滤即可表达；这里加 DISTINCT 是为了避免同一家公司因多件便宜产品而重复输出。

🎯 存在量词＝连接＋过滤＋DISTINCT，容易写。

P97

全称量词：双重否定

考点

难点在全称量词（universal）：「所有产品价格都低于 100 的公司」。课件给的做法是双重否定——找出「不存在任何价格不低于 100 的产品」的公司，写成 SELECT DISTINCT Company.cname FROM Company WHERE name NOT IN (SELECT company FROM Product WHERE price >= 100)。注意这页抽取文本有残缺（子查询只剩 Product.price >= 100），按语义补全就是上面这句。课件标注它与「只产便宜货」等价。

🎯 ∀ 条件 ≡ ¬∃ 反例；NOT IN / NOT EXISTS 是标准写法。

P98

NULL 到底是什么

考点

这页引入 NULL 的语义问题：没有值时填 NULL，而 NULL 可以表示很多意思——值不存在、值存在但未知、值不适用等等。schema 规定每个属性能否为空（nullable attribute），前面讲过 NOT NULL 约束。课件最后提问：SQL 怎么处理带 NULL 的表？答案是三值逻辑，下一页开始展开。先把这条记住：NULL 不是 0，也不是空字符串。

🎯 NULL 有多种业务含义，但计算行为只有一个：未知。

P99

三值逻辑：0 / 0.5 / 1

考点

这页给两条规则。① 数值运算中 NULL 会传染：若 x 是 NULL，则 4*(3−x)/7 仍然是 NULL。② 布尔运算有三个值：FALSE = 0、UNKNOWN = 0.5、TRUE = 1。所以「x 等于 Joe」在 x 为 NULL 时结果不是 FALSE，而是 UNKNOWN——这是后面所有 NULL 坑的起点：WHERE 只接受 TRUE，UNKNOWN 会被丢掉。由此还能推出一条：NULL 不参与任何等值比较，所以它的行永远比不出真假。

🎯 NULL 参与比较得到 UNKNOWN，不是 FALSE。

P100

三值逻辑的运算规则

考点

这页给三值逻辑的运算规则：C1 AND C2 = min(C1, C2)、C1 OR C2 = max(C1, C2)、NOT C1 = 1 − C1，再配一条总规则：WHERE 只保留结果为 TRUE（1）的元组。示例查询要筛 age < 25 且身高体重大于阈值，结果不会返回 age=20、height=NULL、weight=200 这行：height > 6 得 0.5，与其它条件取 min 后仍不到 1，于是被丢弃。把这三个公式记熟，任何带 NULL 的条件都能手算「这行到底留不留」。

🎯 min / max / 1−x 加「只留 TRUE」，NULL 题全靠这四条。

P101

看上去全覆盖，其实漏了 NULL

考点

这页展示一个意外行为：SELECT * FROM Person WHERE age < 25 OR age >= 25，看起来把年龄分成两半、应当覆盖所有人，但结果里有些 Person 没被包含。原因就是 NULL：age 为 NULL 时两个条件都是 UNKNOWN = 0.5，OR 取 max(0.5, 0.5) = 0.5，不等于 1，所以整行被丢掉。这是三值逻辑最经典的例子，出镜率极高。同理，带 NOT 的条件也会因为 UNKNOWN 而漏行。

🎯 「看似覆盖全部」的条件仍会漏掉 NULL 行。

P102

修法：IS NULL

考点

修法是显式判断 NULL：SELECT * FROM Person WHERE age < 25 OR age >= 25 OR age IS NULL，这样 NULL 行也会被包含。注意必须用 IS NULL / IS NOT NULL，不能写 age 等于 NULL——因为 NULL 等于 NULL 的结果是 UNKNOWN，同样过不了 WHERE。记一条铁律：判断空值只能用 IS NULL，任何比较运算符遇到 NULL 都失效。写条件时先问一句「这行可能是 NULL 吗」，再决定要不要补一个 IS NULL 分支。

🎯 判空只能用 IS NULL，不能写等于 NULL。

P103

内连接回顾：两种等价写法

考点

这页回到连接，先复习内连接（inner join）：默认的 join 都是 inner join，两种写法等价——SELECT Product.name, Purchase.store FROM Product JOIN Purchase ON Product.name = Purchase.prodName，与 FROM Product, Purchase WHERE Product.name = Purchase.prodName。两张表是 Product(name, category) 与 Purchase(prodName, store)。也就是说逗号写法就是内连接，别以为它和外连接一样。这两种写法在结果上完全一致，只是风格不同，改写题里可以互相替换；至于内连接会丢行，是下一页的主题。

🎯 逗号写法与 JOIN ON 都等价于 INNER JOIN。

P104

内连接会丢数据

考点

这页点出内连接的问题：从没卖出去过的商品会消失。因为 inner join 只保留两边都能配上对的行，Product 里若有商品在 Purchase 中没有任何记录，它就不会出现在结果里。这不是 bug，而是内连接的定义决定的。若业务要「列出所有商品及其销量，没卖出的显示为空」，就必须改用外连接——下一页开始讲。

🎯 inner join 会丢掉右表没有匹配的左侧行，这是丢数据根源。

P105

外连接：保留没匹配上的行

考点

这页给外连接的定义：外连接会返回那些在另一张表里找不到对应元组的行。具体说，若 A 与 B 按 X 相等连接，A 里有一个 X = 5 的行、B 里没有 X = 5 的行，那么 LEFT OUTER JOIN 会返回 (a, NULL)，即右表各列补 NULL。写法：FROM Product LEFT OUTER JOIN Purchase ON Product.name = Purchase.prodName，这样没卖出的商品也会保留。课件用 A、B 两表的抽象例子讲这件事，是为了让你把结论推广到右外连接与全外连接。

🎯 左外连接：左表全保留，右表缺的补 NULL。

P106

内连接的结果表

考点

这页画出 INNER JOIN 的结果。Product 三行：Gizmo（gadget）、Camera（Photo）、OneClick（Photo）；Purchase 三行：Gizmo 卖到 Wiz、Camera 卖到 Ritz、Camera 卖到 Wiz。内连接按 name = prodName 配对，输出三行——Gizmo Wiz、Camera Ritz、Camera Wiz；OneClick 完全消失，因为它在 Purchase 里没有记录。课件顺带提醒：INNER JOIN 只是另一种写法，与前面两种等价。手算时先把所有匹配对列出来，再检查每张表有没有剩下的行，最后决定要不要补 NULL。

🎯 看结果表：OneClick 不在，就是内连接丢数据的证据。

P107

左外连接的结果表

考点

这页是同一个查询改成 LEFT OUTER JOIN 的结果：前三行与内连接相同，多出第四行 OneClick NULL——OneClick 没卖出去，右表列补 NULL。这就是外连接的用途：保留主表全量。考试常给两张小表问「左连接后几行」，答案等于内连接行数加上左表中没匹配上的行数，这里是 3 + 1 = 4 行。

🎯 左连接行数 = 匹配行数 + 左表未匹配行数（本例 4 行）。

P108

左外、右外、全外

考点

这页总结三种外连接。① 左外连接（left outer join）：即使右表没有匹配，也保留左表的元组；② 右外连接（right outer join）：即使左表没有匹配，也保留右表的元组；③ 全外连接（full outer join）：两侧都保留，缺哪边就补 NULL。注意方向只决定「保留谁」，不改变连接条件；LEFT 与 RIGHT 在交换表顺序后可以互相转换。

🎯 LEFT 保留左、RIGHT 保留右、FULL 两边都保留。

P109

L2 总结：声明式语言

全讲总结：SQL 是一门声明式、功能丰富的编程语言，它描述「数据要怎么被处理」，而把「怎么执行」交给优化器。回看整讲：Part I 是建表与基本查询（单表、多表），Part II 是集合运算、嵌套、聚合分组、NULL 与外连接。复习顺序建议：先默写 SFW 骨架，再依次补上 GROUP BY、HAVING、join 语义与 NULL 三值逻辑。
